Parrilla BI

End-to-end Business Intelligence project based on a simulated restaurant operation, built with SQL Server, Power BI and dimensional data modeling.

The project is currently evolving from a static analytical solution into a Data Engineering pipeline using Python, API ingestion, RAW/STAGING layers and ETL.

---

## About the Project

Parrilla BI started from a simple question:

> How can operational restaurant data be transformed into useful information for business decisions?

The dataset simulates 24 months of restaurant operations and was created to practice the complete analytical workflow — from database modeling and data validation to SQL analysis, Power BI dashboards and business storytelling.

The current version contains:

- 78,916 orders
- 219,044 order items
- 29,825 deliveries
- 3,600 customers
- 135 products

The project is based on synthetic data and does not contain real customer or company information.

---

##  Project Goals

The first stage of the project focused on building an analytical environment capable of answering questions such as:

- Where does revenue come from?
- Which products and categories generate the most revenue?
- How does sales performance change over time?
- Which sales channels concentrate the highest order volume?
- What is the average order value by channel?
- How can employee and commission data be incorporated into the analytical model?

The next stage introduces Data Engineering concepts to simulate how new operational data could be generated, ingested, processed and delivered to the analytical layer.

##  Current Architecture — V1

The current analytical flow is:

```text
Synthetic CSV Dataset
        ↓
    SQL Server
        ↓
Dimensional Analytical Model
        ↓
      Views
        ↓
     Power BI
        ↓
Analysis & Storytelling



The original CSV files were loaded into SQL Server using BULK INSERT.

After ingestion, the data was validated for integrity, relationships and financial consistency before being consumed by the analytical layer.

The project currently contains two main analytical pages.

The second page was developed with a stronger focus on storytelling and business interpretation.

Instead of only showing which channel generates the most revenue, the analysis combines:

Revenue × Number of Orders × Average Ticket

This makes it possible to investigate why one channel generates more revenue than another.

Current results:

Channel	Revenue	Orders	Average Ticket
Salão	R$ 4.46M	37,360	R$ 119.30
Delivery	R$ 3.53M	29,825	R$ 118.20
Retirada	R$ 1.39M	11,731	R$ 118.27

The average ticket is very similar across the three channels.

Therefore, the higher revenue generated by the restaurant floor is primarily explained by sales volume rather than by a significantly higher average ticket.

🧱 Planned Data Layers
RAW

The RAW layer will store the payload received from the source with minimal transformation.

Its purpose is to preserve what was originally received by the ingestion layer.

STAGING

The STAGING layer will store structured and validated data prepared for transformation and loading.

Planned processing includes:

type normalization
validation
deduplication
separation of orders and order items
error handling
Data Warehouse

The dimensional model already developed in SQL Server will become the analytical destination of the pipeline.

The objective is to preserve the current BI model while changing how new data reaches it.

💡 Key Learning

One of the main lessons from this project has been that building a dashboard is not only about choosing charts.

The analytical process increasingly became:

Business Question
      ↓
SQL Analysis
      ↓
Metric
      ↓
Visualization
      ↓
Insight
      ↓
Hypothesis
      ↓

The next challenge is applying the same reasoning to the engineering side of the project:

Not only analyzing the data, but understanding how the data should be generated, ingested, transformed and delivered for analysis.
